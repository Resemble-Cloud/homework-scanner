# 曲面展平 Spike 报告（v1.1 Phase 3）

- 分支：`spike/freebuff-dewarp`
- 基线：`main` @ `670c975`
- 原型：[tools/dewarp_spike.py](../tools/dewarp_spike.py)（Python + OpenCV + NumPy，无新依赖）
- 数据：[docs/quality/dewarp/metrics.csv](quality/dewarp/metrics.csv)
- 对比图：[docs/quality/dewarp/](quality/dewarp/)（3 档曲率 + 3 个失败案例）
- 复现：`python tools/dewarp_spike.py`（自带模型自检，十几秒到一分钟半）；只跑自检：`python tools/dewarp_spike.py --selftest`
- 本轮**不改** `lib/`、`packages/fairscan_engine/`、`android/`，不接 UI，不引入任何模型。
- **v2 修订**（见第 11 节）：v1 的 `forward` 模型有恒等映射 bug，真值位移场和两种方法的位移场都少了水平分量，v1 报告里的 PSNR 增益比例与位移误差全部作废。本版数字是修好模型后重算的。

## 1. 结论

**不要移植，而且理由比 v1 更强：上限很高，当前原型只兑现了一小部分，并且估计失败时会主动把图改坏。**

- 用**真参数**做完整反解，PSNR 能到 **29.6–30.6 dB**（SSIM 0.986–0.989），比不校正高 **13–16 dB**。也就是说「弯曲单页、文字为主、纸边清晰」这件事在几何上几乎可以无损还原，**天花板远没有被摸到**。
- 两个方法都没拿到多少：方法 B（圆柱反解）只兑现了理论上限增益的 **30% / 20% / 25%**（+4.31 / +3.09 / +4.13 dB），方法 A（文本行垂直拉直）只有 **3.8% / 6.0% / 5.5%**（+0.54 / +0.91 / +0.90 dB）。
- 位移误差（对弯曲照片坐标）：不校正时中位 1.75 / 3.03 / 5.92 px。方法 B 压到 **0.55 / 0.95 / 1.62 px**（消掉 69% / 69% / 73% 的中位量），但 P95 仍有 **3.39 / 6.14 / 10.83 px**；方法 A 只压到 1.71 / 2.56 / 4.77 px（只消掉 2% / 16% / 19%），因为它不动水平压缩。
- 瓶颈已经定位得很具体：纸面边界曲线只能定标 **`R` 与 `focal` 的某种组合**，水平分量定不下来；估计一旦崩（低对比桌面）模型会照做，PSNR 从 15.07 掉到 11.76、位移误差中位 23.34 px（比不校正差 7 倍）。
- 所以下一轮该做的是 **真实样张验证 + 估计自检 + 联合定标水平方向**，**本轮不写 Kotlin，拿到真实样张和自检之前也不建议写**。

## 2. 闭环设计

`test_assets/fixtures/page.jpg` 实际是一张「空表格」（黑边框 + 顶部两条长横线），所以脚本只取它中间的空白纸面当纸纹理，再自绘内容：

- 内容：11 行正文，每行 = 一条基线速写 + 一列竖笔画（模拟字母），行距约 71 px。**竖笔画是刻意加的**：只有横线条的页面在 PSNR 上对水平错位几乎不敏感（见第 4 节），会低估水平压缩的伤害。
- 照片：700×950 的纸页贴在 900×1200 的暗桌面上（桌面 58–84 灰阶 + 噪声）。
- 弯曲（ground truth，已知参数）：

```
theta = (x - cx) / R        # 平面上的弧长 → 圆心角
x'    = cx + R * sin(theta)                     # 水平压缩，边缘最多
s     = focal / (focal + R * (1 - cos(theta)))  # 越远缩得越小
y'    = cy + (y - cy) * s                       # 文本行向画面中心弓起
```

- 3 档：`level1_mild` R=900、`level2_medium` R=600、`level3_strong` R=380，`focal=1600`，`cx/cy` = 画幅中心。纸页横跨画幅中心两侧 ±360 px，实测纸面左右边缘的水平压缩量 **9.5 / 21.2 / 51.5 px**，纸面顶部文字行的最坏纵向位移 **17.6 / 25.4 / 37.1 px**（行距 71 px，即接近半行）——这是「中度到偏强」的弯曲，不是极端卷曲。
- 正向 warp 生成弯曲照片，两个方法各自尝试还原，与平面 ground truth 逐像素比较。
- **模型自检**：`selftest()` 在算任何指标前先验证 `forward ∘ inverse` 与 `inverse ∘ forward` 都是恒等（误差 < 1e-6 px）、`forward` 在边缘确实压缩（不是恒等映射）、且压缩量等于解析值 `R*(sinθ − θ)`。任一不过就直接 `SystemExit`，不出指标。这是 v1 那个 bug 的守卫。

## 3. 两种方法

**方法 A：文本行拟合（只修垂直）**

自适应阈值 → 水平形态学连接（核宽 = 图宽/18）→ 连通域筛「够宽够扁」的行带 → 逐列取该行带最下方墨迹行作为基线 → 以**纸面水平中心列**（弯曲模型在该处是恒等）为各行目标行 → 对每一列用全部行节点做最小二乘拟合 `shift(x, y) = a(x) + b(x) * y`（比在相邻行之间做分段线性更稳，也不会把行距改形）→ 平滑 `a(x)`、`b(x)` → 逐列 remap。**不做水平校正。**

**方法 B：页面边缘 / 圆柱模型（垂直 + 水平）**

Otsu + 最大连通域分割纸面 → 逐列取纸面上下边界曲线 → 网格搜索 `(R, focal, cy)`（45×7×25 组），用上下两条边界曲线的最小二乘残差定标。注意定标发生在**照片坐标**上：每个观察列 `x'` 先求 `θ = arcsin((x' − cx)/R)`，再由 `s = focal/(focal + R(1−cosθ))` 预测边界 y。拿到 `(R, focal, cy)` 后用解析 forward 把整幅**平面网格**映射回弯曲照片并 remap。只用纸面轮廓，不看内容。

## 4. 指标

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| 文本行直线度 | 每一行带基线曲线（宽平滑后）在 x 方向的 std，px | 越小越直 |
| PSNR / SSIM | 与平面 ground truth 在纸页内部（内缩 6%）比较 | 越大越好 |
| 位移误差 中位 / P95 | 输出像素取到的源点 vs ground truth 源点，在弯曲照片坐标下的距离，px | 越小越好 |
| 耗时 | 单次调用，900×1200 | 记录 |
| 行带数 | 该图上检出的行带数量（检测是否崩掉） | 参考 |

**指标本身的局限（重要）**：这套合成内容上 PSNR/SSIM 对「只修一个轴」并不敏感 —— 用真参数只修垂直是 18.64 / 17.18 / 14.46 dB，只修水平是 18.56 / 17.16 / 15.80 dB，两者几乎一样，远低于完整反解的 ~30 dB，但也都比不校正好 1–2.6 dB。原因是弯曲的垂直位移（最坏约 38 px，接近半个行距）与水平位移在逐像素比较里会互相干扰。所以**PSNR/SSIM 只能作为辅助，排序主要看位移误差**，而位移误差只有在有 ground truth 的合成样本上才能算。

**理论对照表**（用真参数分别做全反解 / 只修垂直 / 只修水平，脚本每次运行都重算并写入 CSV 的 `*_th_*` 列，不再是手算）：

| 案例 | 不校正 PSNR | 只修垂直（真参数） | 只修水平（真参数） | 完整反解（真参数） | 完整反解 SSIM |
| --- | --- | --- | --- | --- | --- |
| level1_mild | 16.36 | 18.64 | 18.56 | **30.55** | 0.9886 |
| level2_medium | 15.07 | 17.18 | 17.16 | **30.20** | 0.9877 |
| level3_strong | 13.19 | 14.46 | 15.80 | **29.63** | 0.9863 |

位移误差中位（真参数）：完整反解 0.00 px（只剩重采样），只修垂直 0.75 / 1.69 / 4.18 px，只修水平 1.17 / 1.74 / 2.69 px —— **单修一个轴都只能消掉一半左右的位移**。

## 6. 关键发现

1. **纸面轮廓只能定标 `R` 与 `focal` 的组合，水平分量定不准。** 方法 B 拟合出的 R 是 1534 / 483 / 483（真值 900 / 600 / 380），边界残差却只有 0.90–1.46 px。原因是只有组合 `R*(1−cosθ)/focal` 决定边界的垂直收缩，多组 (R, focal) 给出几乎同一条曲线（本轮的估计里 `R*focal` 大致守恒：1.38M / 1.01M / 0.58M，真值 1.44M / 0.96M / 0.61M）。**垂直方向恢复得好（s(x) 误差 < 0.5%），水平方向只能算「大方向对、标定不准」**——这也正是 B 的中位位移误差被压到 0.55–1.62 px 却再也下不去的直接原因。
2. **真正的天花板很高，但需要「知道参数」而不是「估对参数」。** 完整反解 ≈30 dB，说明剩下的 10 dB 全卡在估计上。任何只靠轮廓的估计方法，都不要期望超过 ~20 dB。
3. **单修一个轴只能消掉三到六成的位移。** 用真参数只修垂直，中位位移从 1.75 / 3.03 / 5.92 px 降到 0.75 / 1.69 / 4.18 px（消掉 57% / 44% / 29%）；只修水平降到 1.17 / 1.74 / 2.69 px（消掉 33% / 43% / 55%）。这解释了方法 A 的兑现率为什么只有个位数：它连「把垂直修干净」都做得不够（A 的中位残余 1.71 / 2.56 / 4.77 px 反而高于真参数只修垂直的 0.75 / 1.69 / 4.18 px，差额来自基线的 ~0.5–2 px 估计误差）。
4. **行带检测本身会被弯曲打崩。** 强弯曲时同一行的 bbox 高度超过「够扁」门限（`bh ≤ 6%` 图高），行带被丢弃：`failure_border_invisible` 里 11 行只剩 1 行通过，方法 A 因此主动放弃（「可用基线不足 → 原样返回」）。这是文本行方案在真实强弯曲页上的一个隐性上限。
5. **两种方法互补**：纸边不可见时 B 退化成一个几乎恒等的映射（R 收敛到搜索上界 6000，PSNR +0.12 dB），此时 A 也因行带崩掉而无事可做；没有文本行时（图表页）A 无事可做而 B 仍能工作（PSNR 18.47 → 22.00）。
6. **错误的估计会让结果更差，必须自带自检**：`failure_low_contrast_desk` 里边界残差 234 px（一个明显不可信的信号），方法 B 仍然照做，PSNR 从 15.07 掉到 11.76、SSIM 0.833 → 0.669、位移误差中位 23.34 px（不校正是 3.03 px）。**任何将来接入的展平都必须以「估计自检通过才改图」为前提。**
7. **和 v1 相比，唯一变好的是「知道自己离上限有多远」。** v1 因为真值位移场少了水平分量，误以为 B 已经拿到 96% 的上限；实际上 B 拿到 20–30%，剩下的空间既大又清楚（水平定标 + 联合估计）。

真实场景里还会碰到这里没覆盖的：手/手指压页、纸面反光、双页摊开、非圆柱形弯曲（斜向弯曲、S 形）、有透视的斜拍（本 spike 的模型里没有相机透视）。**结论只能覆盖「单页、文字为主、纸边清晰、近似圆柱」的情形。**

## 8. 代价

- 方法 A：50–107 ms（900×1200，Python）；只需要灰度 + 阈值 + 连通域 + remap。
- 方法 B：168–565 ms，其中绝大部分是边界参数网格搜索（7875 组 × 逐列残差）；换成解析最小二乘或粗到细搜索可以降一个量级，但仍是「每次扫描多几十毫秒到几百毫秒」的量级，在 4MP 预算的页面上还会放大。
- 两者都需要一次额外的 resize/remap，会带来一次重采样模糊（本 spike 没评估它对小字/上下标的影响）。模型自检本身开销可忽略（本次运行 < 0.01 s）。
- **ms 列是单次墙钟，只表示量级**：重跑一次（同样的输入、同样的种子）得到 A 47–143 ms / B 197–694 ms，与本节引用的那一轮差了约 1.5 倍，其余所有指标逐位相同、对比图字节相同。要做性能对比必须多轮取中位。

## 9. 建议的下一步

1. **不移植 Kotlin。** 先拿 3–5 张真实「轻度/中度弯曲、文字为主、纸边清晰」的照片复核本 spike 的两个方法；没有真实样张之前，任何移植都是在没验证的模型上写生产代码。
2. 若真实样张验证通过，下一轮做**联合估计**：用文本行基线的垂直信息 + 纸面边界的几何约束一起拟合位移场，并对水平压缩用内容信息（字符宽度/纹理）单独定标——单靠轮廓定不了水平方向（第 6 节第 1 条）。
3. 必须同时做**估计自检**：边界残差、行带数、拟合参数越界（贴到搜索上界）都要触发「放弃修改」，宁可退回原图。
4. 真实样张只能放 `test_assets/real_samples/`（本地、已 gitignore），不提交。

## 10. 限制与不做

- 只在合成样本上验证，**不能替代真实样张验收**；合成内容是我自己画的笔画，不是真实作业。
- 没有相机透视、没有纸张纹理建模、没有手指/反光、没有双页与非圆柱弯曲。
- 指标里 PSNR/SSIM 对单轴校正不敏感（第 4 节），排序主要依赖位移误差；`displacement_error` 依赖已知的 ground truth 模型，真实照片上没有这个指标。
- 没有评估重采样对小字/上下标的损失，也没有评估与现有 FairScan 增强链路的先后顺序。
- 不改 `lib/`、`packages/fairscan_engine/`、`android/`，不接 UI，不引入深度学习模型，不新增依赖，不改 App 默认输出。

## 11. 修订记录（v2）

**问题**：v1 的 `Cylinder.forward` 用 `_theta()` 求角，而 `_theta()` 里是 `arcsin(dx/R)`；`forward`   再取 `sin()`，两者相互抵消：

```
forward(x) = cx + R * sin(arcsin((x - cx) / R)) = x        # x 方向退化成恒等映射
```

`inverse`（`bend()` 用它生成合成弯曲图）是正确的一侧，所以**弯曲照片本身没问题**，但：

- `truth_map = truth.forward(gx, gy)` 少了水平分量 → 位移误差只统计了垂直方向（v1 报告的「中位 0.13–0.21 px」由此而来）；
- 方法 B 的 `est.forward(gx, gy)` 是同一个坏函数 → B 实际只修了垂直，v1 说的「垂直 + 水平全反解」不成立；
- v1 的「B 拿到理论上限的 96%」是循环验证：真值和方法 B 用的是同一个错误映射，两者一起错，比例自然接近 1。

**修法**：

1. `_theta` 拆成 `_angle_on_flat`（`dx / R`，弧长转圆心角）与 `_angle_in_photo`（`arcsin`，照片投影转圆心角），`forward` 只用前者、`inverse` 只用后者；`estimate_cylinder` 的 `arcsin` 保持不变（它作用在观察列上，本来就是照片坐标 → 圆心角）。
2. 新增 `selftest()`：验证双向 roundtrip < 1e-6 px、`forward` 边缘确实压缩、压缩量等于解析值 `R*(sinθ − θ)`，失败即 `SystemExit`。用 v1 的 `forward` 跑 `--selftest` 会退出码 1（边缘压缩 0.0 px，压缩量误差 44.3 / 70.0 / 105.0 / 350.0 px，正好是各档的边缘压缩量）。
3. 理论上限表（全解 / 只垂直 / 只水平）从临时脚本移进 `dewarp_spike.py`，逐案例写入 metrics.csv 的 `psnr_th_*` / `ssim_th_*` / `med_th_*` / `p95_th_*` 列，口径与正文一致。
